# Подключение нового сервиса (провайдера)

Этот документ описывает, как добавить в PetCrew третий и последующие наблюдаемые
источники агентов через тот же провайдер-нейтральный протокол, что и Codex и OpenCode.

Каждый новый провайдер — это **адаптер**: локальный модуль, который переводит
события внешнего инструмента в события протокола `1.0` и отправляет их в
авторизованный loopback-хаб PetCrew. UI не содержит провайдер-специфичного кода.

## 0. Решения, которые уже приняты

Новый адаптер обязан соблюдать существующие решения:

- **D-002** — провайдер-нейтральное ядро: UI не парсит специфику провайдера.
- **D-010** — приём событий только через авторизованный loopback-эндпоинт.
- **D-015** — правило видимости «активные + недавние» (норма 100, защищённый переполнение).
- **D-003** — честный прогресс: дроби/проценты только из явного `current`/`total`.
- **D-022** — минимальный реестр агентов пользователя, хеширование идентификаторов.
- **D-037 / D-038** — наблюдательная граница и отложенная загрузка существующих сессий
  после регистрации хуков (применяется по аналогии к любому новому провайдеру).

## 1. Граница адаптера

Адаптер наблюдательный. Он:

- эмитит события протокола `1.0`;
- не отвечает на вопросы, не одобряет права, не управляет сессиями;
- не изменяет аргументы инструментов и не вызывает модель;
- не читает приватные логи, базы данных провайдера, креденшелы и конфигурацию.

Реализация не авторизует установку, перезапуск провайдера или изменение его живой
конфигурации. Это отдельный явный шаг с планом отката (см. раздел 8).

## 2. Идентичность события

Каждое событие несёт обязательные поля из `docs/EVENT_PROTOCOL.md`:

| Поле | Значение |
| --- | --- |
| `protocol_version` | `"1.0"` |
| `provider` | уникальная строка, например `myai` |
| `session_id` | непрозрачный SHA-256 корневой сессии |
| `agent_id` | непрозрачный SHA-256 отдельного хода корня или потомка |
| `parent_agent_id` | SHA-256 родителя или `null` |
| `event_type` | один из типов протокола |
| `event_id` | уникальный идемпотентный идентификатор |
| `sequence` | монотонный номер в рамках `agent_id` |

Идентификаторы провайдера делаются **непрозрачными** (хешируются) до выхода из
адаптера. Сырые технические id не попадают в реестр и логи (кроме транзитного
состояния UI при навигации, если она поддерживается — см. D-025).

Одна сессия может выполнять несколько последовательных ходов. Каждый новый ход обязан
получить новый `agent_id`; повторное использование терминального id приведёт к честному
отказу хаба `409`. `sequence` восстанавливается из последней записи реестра и остаётся
монотонным после перезапуска адаптера.

## 3. Проект

- `project.id`: SHA-256 нормализованной директории проекта.
- `project.name`: только финальное имя директории.
- `project.path`: всегда `null` в состоянии PetCrew.

## 4. Разрешённые и запрещённые поля

**Разрешено:**

- санитизированный заголовок сессии (до 120 символов);
- общее действие, выведенное только из имени инструмента;
- фаза жизненного цикла / внимания;
- явные `current`/`total` из событий плана задач;
- метки времени начала/обновления/завершения;
- общее терминальное резюме.

**Запрещено** (не должно попадать в состояние, реестр и логи):

- промпты, текст сообщений, рассуждения;
- ввод инструментов, shell-команды, вывод инструментов;
- тела ошибок, паттерны/ответы прав, текст вопросов и ответов;
- полные пути, креденшелы, переменные окружения;
- данные авторизации/конфигурации провайдера.

## 5. Отображение событий провайдера

Сопоставьте нативные события провайдера типам протокола:

| Нативное событие провайдера | Тип протокола |
| --- | --- |
| старт сессии/задачи | `agent.started` |
| прогресс плана | `agent.progress` (только явный) |
| активность инструмента | `agent.activity` |
| вопрос пользователю | `agent.attention_requested` (`kind: input`) |
| запрос права | `agent.attention_requested` (`kind: approval`) |
| блокировка/ошибка | `agent.attention_requested` (`kind: blocked`/`failure`) |
| завершение | `agent.completed` |
| сбой | `agent.failed` |
| отмена | `agent.cancelled` |

Семантика завершения: терминальное событие эмитится только если адаптер видел
этого агента активным или ожидающим внимания в текущем сеансе адаптера. Исторические
завершённые сессии, найденные при старте, не должны генерировать новые результаты
(аналогично D-037).

## 6. Существующая работа (bootstrap)

На старте адаптер может прочитать только метаданные активных/занятых сессий через
официальный, документированный API провайдера. Кешируются только идентичность,
заголовок и родитель. Не запрашиваются сообщения, диффы, файлы и база данных.

**Порядок загрузки (критично для D-038):**

1. адаптер регистрирует и возвращает все живые хуки/обработчики;
2. только после этого планируется опциональное восстановление сессий;
3. ожидание сетевого SDK-запроса внутри инициализации запрещено — это может
   вызвать дедлок локального сервера провайдера.

Любой сбой восстановления изолируется и не блокирует живые события.

## 7. Транспорт

Адаптер использует существующий авторизованный loopback-протокол
(`docs/EVENT_PROTOCOL.md`, раздел «Loopback HTTP transport v1»):

- читает `hub-runtime.json` и `hub-secret.txt` из локальной директории Tauri app-data;
- считает дескриптор устаревшим, пока `GET /health` не ответит быстро `200`;
- шлёт `POST /v1/events` с `Authorization: Bearer <secret>`;
- обрабатывает `400/401/409/413/408` как безопасные отказы без вывода тела запроса.

Адаптер не имеет сторонних зависимостей. Все сбои best-effort, ограничены и
неблокирующи для провайдера.

## 8. Шаги подключения (чеклист)

1. Выберите `provider` (например `myai`) и зафиксируйте его в `EVENT_PROTOCOL.md`
   как поддерживаемое значение; добавьте его в JSON Schema и проверки хаба.
2. Создайте адаптер в `adapters/<provider>/` по образцу `adapters/opencode/petcrew.js`.
3. Реализуйте нормализацию идентификаторов (SHA-256) и sanitize полей (раздел 4).
4. Реализуйте регистрацию хуков до восстановления (раздел 6).
5. Реализуйте отправку в loopback-хаб и обработку ошибок (раздел 7).
6. Добавьте изолированные тесты на маппинг, приватность, уникальность ходов,
   монотонную последовательность, неблокирующий старт и health-gated transport.
7. Напишите аудит-документ `docs/<PROVIDER>_ADAPTER_AUDIT.md` и контракт
   `docs/<PROVIDER>_PLUGIN_CONTRACT.md` по образцу OpenCode.
8. **Отдельный гейт:** покажите пользователю точную конфигурацию установки и план
   отката (backup), не применяйте без явного одобрения.
9. Зафиксируйте решение в `_Agents/SHARED/DECISIONS.md` (новый `D-0xx`).
10. Обновите `PROJECT.md` (Important Files) и `_Agents/HANDOFF.md` (Current truth).

## 9. Проверка

- `npm test` и `cargo test` остаются зелёными.
- UI показывает нового провайдера без изменения провайдер-специфичного кода.
- Идентификаторы непрозрачны, запрещённые поля отсутствуют в реестре и логах.
- Защищённое переполнение и правило «активные + недавние» работают для нового `provider`.
